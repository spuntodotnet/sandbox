## A cloud VM with nested virtualization

GCP `n2-standard-8` (Intel Cascade Lake), Ubuntu 24.04, nested virtualization, a 100 GB pd-ssd as
the pool. `small` boxes (1 vCPU, 2 GB). 2026-11-25, Spunto Sandbox 0.1.0, as `sbx` reports them.

| | |
|---|---|
| `sbx run ubuntu:24.04`, first box of the image (pull, unpack in a microVM, boot, agent) | 7.6 s |
| `sbx run ubuntu:24.04`, image already there | 2.5 s (daemon side: 0.54 s to running) |
| `sbx run node:24-slim`, first box (152 MB image) | 12.7 s |
| `sbx pause` of a freshly booted box (all of its RAM written: a *Boot* snapshot) | 0.8 s |
| `sbx resume`, until the agent answers | 0.27 – 0.34 s (daemon side: 0.17 s) |
| `sbx fork` of a running box: source paused | 39 – 77 ms |
| `sbx fork`: the copy running, agent answering | 0.9 – 1.2 s |
| `sbx snapshot` (memory): source paused / memory ready | 0.42 s / 1.5 s |
| `sbx run --from <memory snapshot>` (daemon side) | 0.36 s |
| `sbx stop` / `sbx start` (a cold boot) | 0.8 s / 2.0 s |
| `exec` of `node -e …`, round trip | 0.4 s |

Nested virtualization makes every VM exit dearer: bare metal is faster.

## Bare metal

A bare-metal OVH server (31 GB), measured while the engine was being built for
Spunto Cloud — with Spunto's own agent, so the "agent online" times include a TLS connection to a
remote platform:

| | |
|---|---|
| Firecracker, boot to a login prompt | 2.3 s |
| `snapshot/load` + resume, daemon side | 27 ms (first trial); 55 – 77 ms with MMDS, the knock and drives refreshed |
| Start → agent online, through the platform | 0.34 – 0.43 s over 7 cycles |
| Fork of a box with a base: the source paused | 533 ms (a busy `xlarge`) |
| Copy of a fork: memory ready after the resume | 1.9 s (2 GB merged and cloned) |
| A fork's copy on disk | 14 MB for 1.5 GB of RAM |
| A box from a memory snapshot, agent online | 0.66 s |
| First stop of a cold-booted `xlarge` (*Boot* Diff, 2.4 GB really held) | 27.6 s (a *Full* of 16 GB: 201 s) |
| The next stop (a Diff) | 1.7 s |

### Against QEMU

On the same server, Incus (QEMU): boot in 9 to 11 s, a stop with state in 8.6 s, its resume in 7.8 s
— no faster than a boot. That measurement is why the engine is Firecracker.

## Integrity

Memory written as Diffs and merged is the part that could silently go wrong. Checked: 1 GB of random
data in `/dev/shm` and 512 MB read back from disk, checksums every 3 s, through boot → load → Diff →
load and through snapshot → copy → Template → load: **no error**. 512 MB zeroed after a snapshot, then
checked in a fork of it: no error (that one caught a real bug — see the design notes, § 17).
